API endpoints
GET /api/months live
Returns all months with expenditure totals. Income and SEPARATE_CATEGORIES (e.g. tuition) excluded from the headline figure but still present as separate keys. 
[{ "month": "2026-07", "expenditure": -52878, "separate_totals": { "Stony Brook": -180000 } }]
GET /api/categories live
Every known category — the fixed list plus anything ever actually assigned to a transaction (including free-text categories typed via the CLI). Backs the frontend's reassignment dropdown, so it never drifts out of sync with what the CLI knows. 
["Eat Out", "Groceries", "Uber", "Online purchases", "Medicines", "Miscellaneous", "Subway", "Amtrak", "LIRR", ...]
GET /api/months/{month}/categories live
Per-category spend for one month. CATEGORY_GROUPS (e.g. Train = Subway + Amtrak + LIRR) rolled into one row. Income excluded — would dwarf routine categories in the chart. 
[{ "category": "Train", "total": 700 }, { "category": "Groceries", "total": -29905 }]
GET /api/months/{month}/categories/{group} live
Real members inside a CATEGORY_GROUP, each with its own net total. Returns an empty array [] for a non-group category. Surfaces the case where one member nets positive (a refund outweighing its charge) even though the group as a whole reads as routine spend. 
[{ "category": "Subway", "total": -11400 }, { "category": "Amtrak", "total": 12100 }]
GET /api/months/{month}/transactions live
All transactions for a month. Amounts always integer cents, sign preserved — formatting (and whether to show sign) is a frontend concern, same convention as the Stripe API. 
{ "id": "8357a96c-...", "transaction_date": "2026-07-13", "description": "WHOLE FOODS MARKET", "amount": -8743, "category": "Groceries" }
PATCH /api/transactions/{id} live
Updates a transaction's category and persists the merchant rule — every future transaction from this merchant auto-applies the new category, same as the CLI's categorization flow. Wired into the dashboard's category-reassignment dropdown. 
// Request body
{ "category": "Dining" }
Key design decisions
Money representation
Integer cents, never floats
IEEE 754 can't exactly represent most base-10 fractions. Amounts enter as Decimal(string), multiply ×100, then int(). Never touches a float at any stage. Same convention as Stripe.
Extensibility
Parser registry pattern
Adding a new bank = one new StatementParser subclass + one dict entry. The ingestion pipeline never changes. No growing if/elif chain.
Data safety
Idempotent inserts
Re-ingesting overlapping PDFs is safe — INSERT OR IGNORE + a UNIQUE constraint on dedup_hash. No pre-check query needed.
Privacy
Fully self-hosted
PDF statements and expenses.db are gitignored. No credentials sent anywhere, no third-party SaaS in the loop. Runs entirely on your own machine via uvicorn today — Docker Compose packaging is on the roadmap, not yet built.
